# Presigned Upload URL -- MCP File Transfer Optimization

**Date:** 2026-05-02
**Status:** Draft
**Problem:** MCP tools force file content (base64 or inline text) through the AI context window, making uploads slow and expensive. A 4-app batch publish moves ~100 KB through the context for no reason.

---

## Goal

Files travel from the agent's filesystem directly to the AIMEAT server over HTTPS, never entering the AI context window. The MCP tool call carries only metadata (< 1 KB), and returns a one-time upload URL.

## Affected Tools

| MCP Tool | Current payload | New upload format |
|----------|----------------|-------------------|
| `aimeat_app_publish` | `content_base64` (24-31 KB) | Raw HTML file via PUT |
| `aimeat_storage_upload` | `data_base64` (up to 10 MB) | Raw file via PUT |
| `aimeat_extension_install` | `manifest` + `scripts: {name: code}` | ZIP (manifest.yaml + scripts/) |
| `aimeat_cortex_install` | `manifest` + `libs: {name: code}` | ZIP (manifest.yaml + libs/) |

## Flow

```
Step 1: Agent calls MCP tool with metadata only (no file content)
        aimeat_app_publish({ filename: "myapp.html", name: "My App", ... })

Step 2: Server validates metadata, generates upload token
        Returns: {
          upload_url: "https://aimeat.io/v1/upload/<token>",
          upload_method: "PUT",
          content_type: "text/html",
          max_size_bytes: 5242880,
          expires_in_seconds: 3600
        }

Step 3: Agent uploads file directly (curl, PowerShell, Python, etc.)
        The file goes from disk to server. Never touches the context window.

Step 4: Server processes the upload (validates, stores, publishes)
        Returns HTTP response JSON:
        { "success": true, "filename": "myapp.html", "version_number": 3, "download_url": "..." }
        OR
        { "success": false, "error": "FILE_TOO_LARGE", "message": "..." }

Step 5: Agent reads the HTTP response. Done.
```

## Inline Fallback

The old parameters (`content_base64`, `data_base64`, `scripts`, `libs`) remain available. If the agent provides inline content, the tool works as before -- no upload URL is returned.

**Decision logic in tool handler:**
- Inline content provided AND size < 1 KB? Process immediately (old path).
- Inline content provided AND size >= 1 KB? Process immediately (old path). Agent chose to use inline.
- No inline content provided? Generate upload URL and return it (new path).

The 1 KB threshold is NOT enforced as a hard limit. It's a recommendation in the tool description. Agents can always use inline for any size (backward compat), but the description guides them toward upload URLs for anything non-trivial.

## Upload Endpoint

### `PUT /v1/upload/:token`

A single generic endpoint that handles all upload types. The token encodes what to do with the data.

**Request:**
- Method: `PUT`
- Body: raw file content (the actual bytes)
- Content-Type: as specified in the upload URL response (e.g., `text/html`, `application/zip`, `application/octet-stream`)
- No Authorization header needed -- the token IS the authorization

**Response (success):**
```json
{
  "success": true,
  "type": "app",
  "filename": "myapp.html",
  "version_number": 3,
  "size": 24576,
  "download_url": "/v1/apps/owner@node/myapp.html"
}
```

**Response (error):**
```json
{
  "success": false,
  "error": "TOKEN_EXPIRED",
  "message": "Upload token has expired (60 min TTL)"
}
```

**Error codes:**
- `TOKEN_EXPIRED` -- older than 60 minutes
- `TOKEN_USED` -- already consumed (single-use)
- `TOKEN_INVALID` -- signature invalid or malformed
- `FILE_TOO_LARGE` -- exceeds max_size_bytes encoded in token
- `INVALID_FORMAT` -- wrong content type or corrupt ZIP
- `VALIDATION_FAILED` -- content fails validation (e.g., invalid extension manifest)

## Upload Token

A signed JWT with short claims, generated by the server.

**Claims:**
```json
{
  "typ": "upload",
  "sub": "alice@aimeat-fi-001",
  "utype": "app",
  "meta": { "filename": "myapp.html", "name": "My App", "category": "tool", ... },
  "maxBytes": 5242880,
  "iat": 1714600000,
  "exp": 1714603600
}
```

| Claim | Purpose |
|-------|---------|
| `typ` | Always `"upload"` -- distinguishes from session JWTs |
| `sub` | Owner GHII or agent GAII who requested the upload |
| `utype` | Upload type: `"app"`, `"storage"`, `"extension"`, `"cortex"` |
| `meta` | Metadata from the original tool call (varies by type) |
| `maxBytes` | Maximum upload size in bytes |
| `iat` / `exp` | Issued at / expires at (60 min window) |

**Single-use enforcement:** The server stores used token JTIs (or a hash of the token) in a short-lived set (TTL = token expiry). On upload, check if already used. If yes, reject. Cleanup: tokens auto-expire from the set after their TTL.

**Signing:** Same Ed25519 keypair used for session JWTs. Verified on the upload endpoint.

## Extension/Cortex ZIP Format

For multi-file uploads (extensions, cortex), the agent builds a ZIP locally and uploads it.

### Extension ZIP structure:
```
extension.zip
+-- manifest.yaml          (the YAML manifest)
+-- scripts/
    +-- init.js
    +-- search.js
    +-- transform.js
```

### Cortex ZIP structure:
```
cortex.zip
+-- manifest.yaml          (the YAML manifest)
+-- libs/
    +-- main.js
    +-- helpers.js
```

**Validation on upload:** Reuses security checks from `package-zip.ts`:
- Magic bytes verification
- Size limits (per-file and total)
- Zip bomb detection (decompression ratio)
- Path traversal prevention
- Manifest presence and validity

**MCP tool description guidance:** The tool description tells the agent:
- "For extension_install: create a ZIP with manifest.yaml at root and scripts in scripts/ directory"
- "For cortex_install: create a ZIP with manifest.yaml at root and libs in libs/ directory"

Agents know how to create ZIPs (zip CLI, PowerShell Compress-Archive, Python zipfile).

## MCP Tool Description Updates

Each affected tool's description must clearly communicate the upload contract. Example for `aimeat_app_publish`:

```
Publish an HTML app. Two modes:

1. UPLOAD MODE (recommended for files > 1 KB):
   Call with metadata only (no content_base64).
   Returns an upload_url. Upload the file with a PUT request
   (curl, PowerShell, Python -- your choice).
   The PUT response contains the publish result as JSON.

2. INLINE MODE (for tiny files < 1 KB):
   Include content_base64 with the base64-encoded content.
   Result is returned directly.
```

## Security Considerations

- **Token is the auth** -- no separate Authorization header needed on PUT. Simplifies agent usage.
- **Single-use** -- prevents replay attacks. Token hash stored in memory/cache until expiry.
- **Bound to type** -- an app upload token cannot be used to upload a storage file.
- **Size-capped** -- max bytes encoded in token, enforced server-side.
- **60 min TTL** -- generous for agents doing multi-step work, but not infinite.
- **Same signing key** -- no new key management. Uses existing node Ed25519 keypair.
- **No IP binding** -- agents may route through proxies. Token possession = authorization.
- **CORS** -- upload endpoint allows cross-origin PUT (for browser-based MCP clients if needed).

- `src/services/upload-token.ts` -- token generation, validation, single-use tracking
- `docs/coding-guidelines/mcp-uploads.md` -- developer guide

### Modified files:
- `src/mcp/apps.ts` -- dual-mode: inline or upload URL
- `src/mcp/core.ts` -- `aimeat_storage_upload` dual-mode
- `src/mcp/extensions.ts` -- `aimeat_extension_install` dual-mode + ZIP support
- `src/mcp/cortex.ts` -- `aimeat_cortex_install` dual-mode + ZIP support
- `src/mcp/index.ts` -- pass upload token service to tool registerers
- `src/server.ts` -- mount upload router
- `openapi.yaml` -- document upload endpoint
- `CLAUDE.md` -- add MCP upload pattern section

### Reused:
- `src/services/package-zip.ts` -- ZIP validation utilities (parseZip security checks)
- `src/auth/jwt.ts` -- JWT signing/verification
- `archiver` + `yauzl` packages -- already in dependencies

## Out of Scope

- Multipart form upload (unnecessary complexity, PUT with raw body is simpler)
- Chunked/resumable uploads (files are max 10 MB, single PUT is fine)
- Client-side encryption (can be added later if needed)
- Upload progress reporting (curl/tools handle this natively)
