## 1. How Apps Are Registered and Served (`src/routes/apps.ts`)

### Storage and URL Pattern

Apps are single-file HTML documents stored in a dedicated `apps` table (not in the memory system). Each publish auto-increments the version number. Old versions are preserved. Screenshots use the existing storage system with key prefix `apps/screenshots/`.

**Routes (all in apps.ts):**

| Method | Path | Auth | Lines | Purpose |
|--------|------|------|-------|---------|
| GET | `/v1/apps` | none | 22-93 | Catalogue listing with search/filter/pagination/federation |
| GET | `/v1/apps/:owner/:filename` | optional | 163-225 | Download app (supports `?version=N`, `?mode=inline`, access code, paid apps) |
| GET | `/v1/apps/:owner/:filename/versions` | none | 96-125 | List all versions |
| GET | `/v1/apps/:owner/:filename/screenshot` | none | 128-161 | Serve screenshot image |
| POST | `/v1/apps` | required | 228-377 | Publish/update an app |
| PATCH | `/v1/apps/:filename` | required | 380-409 | Update access code |
| DELETE | `/v1/apps/:filename` | required | 412-446 | Delete app (supports `?version=N`) |

### Download Endpoint (GET /v1/apps/:owner/:filename)

Two modes:
1. **Attachment mode** (default, line 218): `Content-Disposition: attachment; filename="{filename}"`
2. **Inline mode** (`?mode=inline`, line 216): Sets a CSP header and serves HTML directly in browser

**Server CSP for inline mode** (line 216, exact quote):
```
default-src 'none';
script-src 'self' 'unsafe-inline' blob: https: http://localhost:*;
style-src 'unsafe-inline' https: http://localhost:*;
img-src * data: blob:;
font-src data: https:;
connect-src 'self' https: http://localhost:* wss: ws: data:;
worker-src blob:;
object-src 'none';
frame-src 'self' blob: data: https: http://localhost:*;
frame-ancestors 'self'
```

This is very permissive. `script-src https:` allows scripts from ANY HTTPS origin. `connect-src https:` allows connections to any HTTPS server.

### Manifest Format (via POST /v1/apps body fields)

When publishing through the REST API directly (lines 283-294):
```typescript
const manifest: AppManifest = {
    name: typeof name === 'string' ? name : filename.replace(/\.html?$/i, ''),
    description: typeof description === 'string' ? description : '',
    version: typeof semver === 'string' ? semver : `1.0.${newVersion - 1}`,
    category: typeof category === 'string' ? category : 'utility',
    tags: Array.isArray(tags) ? tags.filter((t: unknown) => typeof t === 'string') : [],
    authorDisplay: owner,
    usesCortex: Array.isArray(uses_cortex) ? uses_cortex.filter((c: unknown) => typeof c === 'string') : [],
};
if (typeof icon === 'string') manifest.icon = icon;
if (typeof price_morsels === 'number' && price_morsels > 0) manifest.priceMorsels = price_morsels;
if (license_type === 'single' || license_type === 'lifetime') manifest.licenseType = license_type;
```

Content is sent as base64 in the `content` field (line 253: `Buffer.from(content, 'base64')`).

### Paid Apps (lines 194-209)

When `config.marketplaceEnabled` and `app.manifest.priceMorsels > 0`:
- Seller can always download their own app (ownerGaii match)
- Others need a valid license (`storage.hasValidLicense()`)
- Returns 402 PURCHASE_REQUIRED otherwise

### Federation (lines 56-84)

The listing endpoint supports `?include_peers=true` to fetch apps from active federated peers. Results tagged with `_peer_node` and `_peer_url`.

### Board Announcement (lines 343-357)

If `config.appAnnouncementBoardId` is set, publishing creates a board post (best-effort, non-blocking).

## 6. App Validation (generator-validate.ts lines 402-420 / generator-validate.js lines 360-378)

### validateApp() -- Identical in Both Files

```typescript
function validateApp(result: string): ValidationResult {
  const errors: string[] = [];
  const html = extractCodeBlock(result, 'html') || result;

  if (!html.includes('<!DOCTYPE html') && !html.includes('<html')) {
    errors.push('Not a valid HTML document -- missing <!DOCTYPE html> or <html> tag');
  }
  if (!html.includes('<head')) errors.push('Missing <head> section');
  if (!html.includes('<body')) errors.push('Missing <body> section');
  if (!html.includes('AIMEAT App Manifest') && !html.match(/name:\s*.+/)) {
    errors.push('Missing AIMEAT App Manifest comment');
  }

  const ap = validateAntiPatterns('app', html);
  errors.push(...ap.errors);

  return { valid: errors.length === 0, errors, extracted: html };
}
```

### validateAntiPatterns for App Type

Only the universal HTML entity check applies (lines 178-199):
- Scans for `&gt;`, `&lt;`, `&amp;`, `&quot;` in code context
- Strips string literals and regex patterns to avoid false positives
- Reports as error if entities found in lines with code characters `=(){}\[\];`

### What IS Checked

1. Contains `<!DOCTYPE html` or `<html` tag
2. Contains `<head` tag
3. Contains `<body` tag
4. Contains `AIMEAT App Manifest` text OR any `name:` pattern (weak fallback)
5. No HTML entities in code context

### What is NOT Checked

- Manifest comment field completeness (name, version, description)
- Manifest comment format validity
- `<meta>` CSP tag presence
- `aimeat-auth.js` loading
- `aimeat-data.js` loading
- `boot()` function presence
- `loadScript()` helper presence
- `auth-container` div presence
- Error collector presence
- Cortex library loading (when cortex exists)
- Empty-state handling
- CSS custom properties usage

## 8. All Discrepancies

### DISCREPANCY 1: CSP Meta Tag vs Server CSP

**Prompt tells AI to generate (meta tag):**
```
script-src 'self' 'unsafe-inline' https://unpkg.com https://cdn.jsdelivr.net;
connect-src 'self' https://*.tile.openstreetmap.org https://cdn.jsdelivr.net https://unpkg.com;
```

**Server sets for inline mode (apps.ts line 216):**
```
script-src 'self' 'unsafe-inline' blob: https: http://localhost:*;
connect-src 'self' https: http://localhost:* wss: ws: data:;
```

When both are present, browsers apply the most restrictive intersection. The meta tag would block scripts from domains other than unpkg.com/jsdelivr.net, even though the server allows any HTTPS domain. The meta tag's `connect-src` would block connections to most HTTPS APIs, even though the server allows `https:`.

This makes the meta tag a **potential footgun** for apps that need external API connections beyond the listed CDN domains. Validation does not check for the meta tag, so some apps may have it and some may not, leading to inconsistent behavior.

### DISCREPANCY 2: Test Page Auth Mock vs Real Auth Library

**Test page mock (generator.ts lines 617-635):**
- `session.fetch()` returns `resp.json()` -- raw parsed JSON from the response body
- JWT is hardcoded inline, no login flow

**Real aimeat-auth.js (as described in app prompt):**
- `session.fetch()` returns an already-parsed object with `.ok`, `.data`, `.error` fields
- Full login flow with `mountLoginButton()` and `AIMEAT.auth.login()`

**Impact:** If app code does `const resp = await session.fetch(url); if (!resp.ok) ...`, it works with the real library (which has an `.ok` field) but may fail in the test page (where `.ok` depends on what the API returned in JSON, not an HTTP status check).

### DISCREPANCY 3: Test Page Data Mock Method Names

**Test page provides:** `AIMEAT.data.put(key, value)`
**App prompt documents:** `AIMEAT.data.set(key, value)`

The test page has `put()` (lines 653-663) but the prompt tells the AI to use `set()`. If the AI follows the prompt, the test page mock won't have the right method.

Additionally, the test page mock is missing `AIMEAT.data.delete()`.

### DISCREPANCY 4: Manifest `entry` Field is Dead

The prompt shows `entry: index.html` in the manifest comment format. The `registerApp()` function does not parse or use this field. It is meaningless metadata.

### DISCREPANCY 5: Weak Manifest Validation

The validator (line 369/411):
```javascript
if (!html.includes('AIMEAT App Manifest') && !html.match(/name:\s*.+/))
```

The `&&` operator means validation passes if EITHER condition is true. A `<meta name="viewport">` tag would satisfy `name:\s*.+`. The validator does not verify that `name`, `version`, or `description` exist inside the manifest comment.

### DISCREPANCY 6: aimeat-data.js Loaded But Undocumented in Cortex Path

When `hasCortex=true`, the boot sequence still loads `aimeat-data.js` (line 580), but the entire `AIMEAT.data` documentation section is skipped (line 596 ternary). The library is available but its usage is not described. If the AI needs to read user preferences or write user-specific data outside of cortex scope, it has no guidance.

## 9. Complete Data Flow

### Generation Path

```
AI generates HTML with manifest comment
  -> validateApp() checks basic HTML structure (5 checks)
  -> Stored in generator memory as component with status "ready"
  -> Register endpoint called
  -> registerApp() extracts manifest from HTML comment
  -> storage.createApp() stores in apps table
  -> App visible in /v1/apps catalog
```

### Serving Path

```
User visits /v1/apps/:owner/:filename?mode=inline
  -> Access code check (if protected)
  -> License check (if paid)
  -> Server sets permissive CSP header
  -> Raw HTML served to browser
  -> Browser loads HTML
  -> loadScript('/v1/libs/aimeat-auth.js')
  -> loadScript('/v1/libs/aimeat-data.js')
  -> loadScript('/v1/cortex/{name}/libs/{name}.js') // if cortex
  -> AIMEAT.auth.mountLoginButton()
  -> AIMEAT.auth.login() -> if session -> startApp()
  -> App calls cortex methods or AIMEAT.data methods
```

### Testing Path

```
Test page served at /v1/generator/test-page/:projectId/:componentId
  -> CSP removed entirely
  -> Auth mock with hardcoded JWT
  -> Data mock with get/getPublic/put
  -> Cortex scripts loaded (all project cortexes)
  -> AI-generated test code runs in page context
  -> Results in window.__testResults
  -> Playwright reads results
```
