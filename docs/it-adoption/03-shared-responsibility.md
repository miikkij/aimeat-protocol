# 03 Shared responsibility

> Checked against AIMEAT node 4.2.0 (commit c1fe5ca66) on 2026-11-04. Maintained with the code: see the README for how.

This page says who does what when an organisation runs AIMEAT as its own system. It is for the security officer, the architect and the DPO who must sign off the split before go-live. Each row names what the software does by itself, what the operator (the organisation's IT) must provide, what organism admins decide, and what each user decides. The detail for each row is on pages 04 to 18; this page is the map. When the organisation runs more than one node (per unit, partner or person), each node has its own operator and this split applies per node ([18 Scope and deployment patterns](18-scope-and-deployment-patterns.md#many-nodes)).

## The four actors

| Actor | Who it is on a node | Source |
|---|---|---|
| **AIMEAT software** | The node process and its defaults, as shipped. | `aimeat/src/` |
| **Operator (IT)** | The organisation that installs and runs the node, and the accounts that hold the node role `operator`. The first account created on a node gets that role; an operator gives it to others and takes it back. | `aimeat/src/routes/setup.ts`, `aimeat/src/routes/admin-monitoring.ts` |
| **Organism admins** | The creator, owners and admins of an organism. An organism is a shared group space with members and workspaces (a team, a department, a partner group). | `aimeat/src/storage/types/organisms-federation.ts` |
| **Users** | People with an account on the node (GHII, a human identity such as `alice@node-id`), and the AI agents (GAII) and apps they approve to act in their name. | [Identity model](../coding-guidelines/identity-model.md) |

## Operator (IT)

- Owns the host, the network, the reverse proxy, TLS, the database server and the file store, and everything below them: OS patches, disk encryption, backups, monitoring.
- Owns the node configuration: `.env` and the admin Config page (`aimeat/src/services/config-schema.ts`). A setting that must take a deploy to change can be sealed with `AIMEAT_SEALED_CONFIG_KEYS`, and then no operator session can change it (`aimeat/.env.example`).
- Owns the trust decisions the node cannot make: which identity provider, which tenants, which AI providers, which outside MCP servers, which apps open to the internet.
- Holds the operator role, which is a role on the account. An agent of an operator acts as operator only for the words the operator ticks for that agent, such as `operator:admin` (`aimeat/src/services/operator-principal.ts`, `aimeat/src/utils/scope-coverage.ts`).
- Is the controller's technical arm for GDPR: runs the export and erasure on request, keeps the processing record current (14).
- Keeps the last access to the content of the node, because the operator answers for what the node holds. Each read, search, delete, restore or export of another person's records is recorded in the operator's usage stream and on that person's account feed (`aimeat/src/services/operator-access-audit.ts`). Content that must stay out of the operator's reach belongs on a node its owner runs ([18 Scope and deployment patterns](18-scope-and-deployment-patterns.md#operator-access-is-a-design-decision)).

## Organism admins

- Invite and remove members, grant each member `viewer` (read) or `contributor` (read and write) on a workspace (`aimeat/src/services/workspace-roles.ts`).
- Classify the organism and its workspaces; everything inside is classified at least that high ([Data classification](../data-classification.md)).
- Hand on workspaces when a member leaves. When an account is erased, the organism passes to another admin or member, or is left without a seated owner when there is nobody (`aimeat/src/services/owner-erasure.ts`).

## Users

- Approve each agent and each AI chat connection, choose its scopes, narrow or remove it later (04, 13).
- Choose who may open and see their apps, records, files and shares, within the limits the operator and the classification set.
- Make the decisions the node keeps for a person in person: raising an agent's clearance, a classification exception, account security changes (04).

## Limits

- The node does not encrypt user data at rest (memory records, workspace documents, stored files, logs). Data encryption at rest is the operator's disk, database and file store encryption.
- The node does not terminate TLS. A node reached without a TLS proxy sends credentials in clear text.
- Two-step sign-in is not required by default (`AIMEAT_TWO_STEP_REQUIRED=off`), and password sign-in is on for everyone by default (`AIMEAT_PASSWORD_SIGN_IN=on`) (`aimeat/src/config-types-account-security.ts`). The node does not check the MFA of an IdP sign-in; that is the IdP's policy.
- The node has no built-in backup schedule; the admin JSON backup is not a backup of the node.
- Logs go to standard output only; there is no syslog, SIEM or log-shipping connector in the node.
- Any account can publish an app inside the node; there is no operator approval before an app is visible to the audience its owner chose. Approval exists only for opening an app to the internet on a closed node and, with `AIMEAT_PUBLISH_GATE`, for an agent or app making something public.
- No node key rotation procedure was found in the code. A leaked node key lets its holder sign tokens the node accepts until the key is replaced, and replacing it ends every issued token, because the token keys are derived from it ([Key rotation](../operations/key-rotation.md)).
- Several safe values are not the code defaults: `AIMEAT_REGISTRATION_MODE` is `open`, `AIMEAT_CONTENT_ACCESS` is `open`, `AIMEAT_PUBLISH_GATE` is `off` and `AIMEAT_CLASSIFICATION` is `off` unless the operator sets them (`aimeat/.env.example`). `aimeat init` writes `AIMEAT_PUBLISH_GATE=agents-and-apps` when the variable is not set (`aimeat/src/cli/init-wizard/steps-core.ts`).
