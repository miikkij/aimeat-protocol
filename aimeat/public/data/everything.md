# AIMEAT Feature List

**What an AIMEAT node does today.** Node version 4.1.2, checked against the code on 2026-10-18; the MCP row on 2026-10-20; the records of processing and the security classes on 2026-10-23; one app open to the internet on a closed node on 2026-10-25; the Messages list's browser copy on 2026-10-25; goals for your agents on 2026-10-25.

AIMEAT (AI Memory Exchange and Action Transfer) is a place where a person keeps what they know, and where their own AIs, other people's AIs and the apps they build can read it, act on it and share it, under the person's consent. The main road in is the AI chat the person already uses, connected over MCP. The web pages show what happened and hold the controls that need a screen.

This list covers two layers:

- **Core** is the protocol any node can implement: identity, memory, consent, organisms and workspaces, pacing, federation. Specified in [AIMEAT-Core-2026-11.md](https://github.com/miikkij/aimeat-protocol/blob/main/docs/AIMEAT-Core-2026-11.md), normative since node 4.0.0; before it, [AIMEAT-RFC-v4.0-Core-full.md](https://github.com/miikkij/aimeat-protocol/blob/main/docs/AIMEAT-RFC-v4.0-Core-full.md) with its errata.
- **Platform** is what the aimeat.io reference implementation builds on it: apps, the agent fleet, extensions, AI, commerce, the web surfaces. This list is its inventory, and the [Platform reference](https://github.com/miikkij/aimeat-protocol/blob/main/docs/AIMEAT-Platform-reference.md) says how it is put together; it replaces [AIMEAT-RFC-v4.0-Platform-full.md](https://github.com/miikkij/aimeat-protocol/blob/main/docs/AIMEAT-RFC-v4.0-Platform-full.md) since node 4.0.0.

The API contract is [openapi.yaml](https://github.com/miikkij/aimeat-protocol/blob/main/openapi.yaml). Where this list and the contract disagree, the contract wins. Individual apps built on the node (Lifecycle Central, the Design Book's apps, games) are not listed here; they are users of these features.

**Markers.** `[off]` means the feature ships but stays off until the operator switches it on. `[testnet]` means it defaults to a test network. Unmarked features are implemented; use can still require configuration, credentials, permissions or an installed runtime. This guide does not report which services a particular node has enabled.

**Reach** names the REST prefix and the MCP tool family, so a developer can find the door. An MCP tool family written `aimeat_task_*` means every tool starting with that name.

## 1. Connecting an AI

The preferred way to use AIMEAT is to talk to it through your own AI. Everything below exists so that the chat path works first and the screen is the fallback.

| Feature | What you get | Reach |
|---|---|---|
| <a id="g-1-mcp-server"></a> **MCP server** | Claude, ChatGPT, Codex, Cursor, VS Code, Grok and other MCP clients can read and act on your node from the chat. The server advertises its available tools when the client connects. | `/v1/mcp` |
| <a id="g-1-purpose-sized-mcp-surfaces"></a> **Purpose-sized MCP surfaces** | Eight opt-in tool sets, so an agent sees only the tools its job needs: `appdev`, `agent`, `service`, `admin`, `commerce`, `primitives` (13 tools, everything else through discover and invoke), `chat` (the node's own chat: about twenty tools at the start, the rest switched on when a job needs them) and `full`. `/v1/mcp` stays the complete, frozen set. | `/v2/mcp/<surface>` |
| <a id="g-1-choose-permissions-when-you-connect"></a> **Choose permissions when you connect** | The approval window for claude.ai, ChatGPT and other services lets you pick read-only, standard, full access, or exactly the permissions you tick, before the connection completes. It names the service by the name it registered with, explains in plain words that the service becomes one of your agents and what an agent is, and says who runs this server with their contact and privacy policy. A line about morsels appears only when the operator paces agents. | OAuth consent screen, `GET /v1/wallet` (`pacing`) |
| <a id="g-1-hello-mcp"></a> **Hello MCP** | One prompt shows the AI is connected, and your profile carries the mark it writes. | <a id="g-1-handbook"></a> **Handbook** | The first thing a connected AI reads: what this node is and which few tools matter for the job in front of it. | <a id="g-1-what-this-node-can-do-for-your-ai"></a> **What this node can do, for your AI** | This list, in parts your AI can read: the areas first, then one area with every feature, what it gives and where it is reached. | <a id="g-1-what-a-setting-means-for-your-ai"></a> **What a setting means, for your AI** | The explanations the pages show behind the question mark next to a setting, readable by your AI: a list of the settings by area, then one setting in full, with what it does, its range, what a lower and a higher value give, examples and when to change it, in English, Finnish and Spanish. Ask your AI what a setting does or which value to pick, and it answers in your language with the same words the page uses. | `aimeat_handbook_get { tier: "settings" }`, `/v1/prompts/settings/sections` |
| <a id="g-1-your-path-from-your-ai-to-what-others-use"></a> **Your path, from your AI to what others use** | Your home shows where you are on seven stages, and the first is your profile: your AI interviews you about your work, what you need, what is hard, what you repeat and what is unclear, and turns the answers into a one-page business card that people open and other AIs read (a schema.org profile in the page). Then: a good AI, connected here, a place for your work, apps, agents at work, and shared with others. A stage is ticked when the account really holds it. The interview works on every road: over MCP, or as a prompt to copy into an AI that cannot connect, with the card pasted back; either way your answers stay private in your own record, and every later offer (a shared place, an app, an agent that takes the repetitive work) is read from them. The help page, the settings overview and the chat offer the same next step. Your own AI reads the same path at the end of its handbook and walks you along it one stage per conversation. | Home · `GET /v1/home/state` (`journey`) · `journey.state` · `/v1/prompts/welcome-mat` · skills `aimeat-guided-journey`, `aimeat-first-conversation` |
| <a id="g-1-start-here-on-every-main-page"></a> **Start here, on every main page** | The main pages (memory, shared places, agents, connect your AI, wallet, access, packages, apps, notebook, AI) open with what the page is for, the one thing to do first as a prompt to copy into your AI or a button, and what happens next. Fold it away once you know the page. Each page title has a question mark that explains its word in plain language. | Settings & Controls |
| <a id="g-1-capability-hints"></a> **Capability hints** | Your AI is told what else the node makes possible and mentions it rarely, when it fits. You switch it off on the MCP page or by telling the AI to stop. | Profile › MCP |
| <a id="g-1-aimeat-connect-cli"></a> **`aimeat connect` CLI** | One command creates a dedicated agent and writes the MCP settings for Goose, Claude Code, Claude Desktop, Cursor or VS Code, without writing your key into a settings file. Also runs as a local stdio MCP server and an ACP bridge. Limits: `--surface` (a smaller tool set) is used by Claude Desktop only; the other clients get the full tool set, and the command says so. | `aimeat connect client <name>` |
| <a id="g-1-watch-the-connector-in-the-terminal"></a> **Watch the connector in the terminal** | A full-screen view of the running connector: how long it has run, its CPU and memory, the traffic to the node and from local clients, each agent's connection, and deliveries as they arrive. Tab shows one agent's open tasks or inbox. It only reads, so it can stay open beside a running crew. | `aimeat connect tui` |
| <a id="g-1-downloadable-client-config"></a> **Downloadable client config** | Pick your client on the page and save the config file the node generates. | `connect-install` |
| <a id="g-1-prompt-driven-road"></a> **Prompt-driven road** | For AIs that cannot connect over MCP (a consumer Gemini app outside the United States, Copilot without Copilot Studio), the pages compose a ready prompt, you run it in your chat and paste the result back. Free and vendor-neutral. A name two apps share (Gemini, Microsoft Copilot) raises one question, which of the two you use, and your answer picks the road. On the home, "My AI can't connect" gives the profile interview as a prompt and turns the pasted answer into your profile card, keeping your answers private. | Contacts, Email, Workflows, Portfolio, front page and home layout pages |
| <a id="g-1-attach-another-mcp-server"></a> **Attach another MCP server** | Attach your Jira, wiki or another service once. Your own AI, agents, apps and this node's chat can use its tools with the permissions you give them. The node stores the credential encrypted and makes the calls, so each client does not need a copy. Hosted servers can use Streamable HTTP or the older SSE transport, with a bearer token, a named API-key header or no sign-in. Attaching and managing need an explicit permission excluded from full access. This node's own address is refused, and a call that would come back to a node it already passed through, for example between two nodes that attached each other, is stopped with 508. | [Settings & Controls > Access > MCP servers](/spa.html#access) · `POST /v1/mcp-servers` · `aimeat_mcp_attach` · `mcp:manage` |
| <a id="g-1-sign-in-to-an-attached-mcp-server"></a> **Sign in to an attached MCP server** | MCP OAuth lets you approve access at the service itself. Choose sign-in when attaching through Access or REST, then complete the consent screen in your browser. The node stores the tokens and refreshes them when supported. Your AI can start the sign-in and hand you the link; it cannot approve for you. A failed renewal asks you to sign in again. | `POST /v1/mcp-servers` with `auth: oauth` · `POST /v1/mcp-servers/{id}/authorize` · `aimeat_mcp_authorize` |
| <a id="g-1-use-what-you-attached-from-chat"></a> **Use what you attached, from chat** | Ask your AI which servers you can use, inspect a server's tools and input schemas, then call a tool by name. The node's chat uses the same MCP access through its own agent. An app calls a tool over REST when you give it the `mcp:use` permission on its consent screen; it never sees the server's address or credential, and it cannot attach or remove a server. Tool discovery can be refreshed when the service changes. A tool's refusal is reported separately from an unreachable server or expired credential. | `aimeat_mcp_list` · `aimeat_mcp_tools` · `aimeat_mcp_call` · `GET /v1/mcp-servers/{id}/tools` · `POST /v1/mcp-servers/{id}/call` · `mcp:read`, `mcp:use` |
| <a id="g-1-manage-attached-mcp-servers"></a> **Manage attached MCP servers** | See server status and tools beside Connected accounts on the Access page. Switch a server off without deleting its setup, turn it back on, or remove it and its stored credential. Your AI or REST also changes its display title or description; the page does not. Removing a server does not revoke a token you created at the outside service; revoke that there too when ending access. | [Access > MCP servers](/spa.html#access) · `PATCH /v1/mcp-servers/{id}` · `DELETE /v1/mcp-servers/{id}` · `aimeat_mcp_update` · `aimeat_mcp_detach` |
| <a id="g-1-narrow-one-agent-to-named-tools"></a> **Narrow one agent to named tools** | Allow a coding agent to read Jira while withholding tools that change tickets. A grant can narrow one agent, one app (written as `app:owner/file`) or everyone acting for you to named tools, on your own server and on a server the node offers to every owner; there it narrows only your own agents and apps, and another owner's grant never touches yours. Fixed arguments override the caller's values, for example keeping requests in the SUPPORT project. An exact grant takes precedence over the default grant for everyone. Grants narrow existing permissions; they do not create access. | `aimeat_mcp_grant_list` · `aimeat_mcp_grant_set` · `GET /v1/mcp-servers/grants` · `PUT /v1/mcp-servers/{id}/grants` · `tools`, `locked_input`, `grantee` |
| <a id="g-1-read-only-access-to-a-server"></a> **Read-only access to a server** | Let an agent read from a server and never change anything on it, for example an agent that reads security alerts but must not block an address. A read-only grant admits only the tools the server itself marks as read-only. A tool without that mark is refused, and so is a tool the server adds later until the server marks it. Limits: the decision rests on the server's own description of each tool, so a server that marks a changing tool as read-only is trusted. | `aimeat_mcp_grant_set` with `read_only` · `PUT /v1/mcp-servers/{id}/grants` (`read_only`) |
| <a id="g-1-mcp-call-limits-and-grant-expiry"></a> **MCP call limits and grant expiry** | Set a rolling call limit and an end date for an agent or app's grant. Expiry blocks calls until the grant is changed or removed. The call limit counts recorded successful calls and is best-effort: concurrent calls or unavailable usage records can exceed it. Replacing a grant replaces its earlier restrictions. Removing it restores scope-based access, so revoke the agent's use permission when you mean to stop access. | `aimeat_mcp_grant_set` with `call_cap`, `expires` · `aimeat_mcp_grant_revoke` · `DELETE /v1/mcp-servers/{id}/grants/{grantee}` |
| <a id="g-1-a-server-s-own-tools-in-your-tool-list"></a> **A server's own tools in your tool list** | Opt a personal server into direct tool listing, called flattening. Permitted tools appear individually with a server prefix, such as `jira__search`, so your AI can select them directly. The gateway remains available for the rest. This currently covers personal servers; selecting flattening on a node-wide registry entry does not yet add its tools. Direct listing describes top-level arguments; the upstream server validates the full schema. | `aimeat_mcp_update` with `exposure: flatten` or `gateway` · `PATCH /v1/mcp-servers/{id}` |
| <a id="g-1-the-node-s-own-mcp-registry"></a> **The node's own MCP registry** | The operator can attach a server for everyone with an account or for named owners only, and set a price per call. No availability policy, or an empty allowlist, offers it to nobody. A price is in money only: morsels pace how much gets used and are never a price, so a morsel price is refused. Proxied calls cannot take payment yet, so a server with a money price refuses its calls by name until they can; leave it free for now. Only the operator attaches, changes or removes a node-wide server, in person or through their own agent holding `operator:admin`. | `POST /v1/mcp-servers/node` · `PATCH /v1/mcp-servers/node/{id}` · `aimeat_mcp_registry_list` · `aimeat_mcp_registry_set` |
| <a id="g-1-a-server-that-belongs-to-a-team"></a> **A server that belongs to a team** | An organism owner or admin can attach the team's wiki to the group, keeping its credential with the group rather than one member. Membership governs the shared server's visibility and intended use. Attachment and membership-aware REST listing are implemented. Group servers are not yet resolved by the ordinary REST and native MCP tool-list and call routes, so attachment alone does not provide a working shared call path there. | `POST /v1/mcp-servers/organism` · `aimeat_mcp_attach` with `organism_id` · `GET /v1/mcp-servers` |
| <a id="g-1-workspace-mcp-access"></a> **Workspace MCP access** | Bind a group's server to one workspace to use that workspace's roles. The access policy allows contributors to call, lets viewers see the server, and excludes group members with no workspace role. Limits: the workspace id is not checked when you attach, so a wrong id lets nobody in; this binding shares the group call-path limitation above. | `POST /v1/mcp-servers/organism` · `aimeat_mcp_attach` with `organism_id` and `ws` |
| <a id="g-1-attached-tools-are-findable"></a> **Attached tools are findable** | Attached tools appear individually in discovery within your own access, so you can search for a task such as opening a ticket. Entries describe the tool and its server without exposing the outside address or credential. Disabled and unavailable servers are excluded. Discovering an entry does not grant permission to call it. | `aimeat_discover` with `scope: own` · discovery source `remote-mcp` |
| <a id="g-1-publish-an-attached-tool-as-a-capability"></a> **Publish an attached tool as a capability** | Give an attached tool a reusable capability description that apps and agents can discover and invoke. Invocation uses the caller's accessible server and credential, with its call restrictions and price. Publishing your Jira capability does not give other people access to your Jira account. Limits: an attached tool is published over REST (you, or an agent holding `capability:write`); `aimeat_capabilities_create` makes only manual capabilities, so your AI cannot publish an attached tool from the chat. | `POST /v1/capabilities` with source type `mcp`, reference `server/tool` · `aimeat_capabilities_invoke` |
| <a id="g-1-mcp-usage-and-refusals"></a> **MCP usage and refusals** | Proxied calls record the caller, server and tool, duration and outcome in the usage stream. Operators can inspect these records to explain what an agent used and why a call was refused. Refusals recorded by the call service are separate from transport errors; not every rejection before that service produces a usage row. | Usage surface `mcp-remote` · `GET /v1/admin/usage/calls` |
| <a id="g-1-another-aimeat-node-as-a-server"></a> **Another AIMEAT node as a server** | Name a peer node instead of entering its address. The node resolves the peer's current address on every call and requires an active peering with routing allowed. Ending the peering or removing routing stops calls through this attachment. The peer's own authentication requirements still apply. | `POST /v1/mcp-servers` · `aimeat_mcp_attach` with `peer` |
| <a id="g-1-a-local-mcp-server-on-the-node"></a> **A local MCP server on the node** `[off]` | The operator can attach an MCP server program running on the node's own host over stdio. It requires both the local-process switch and an allowlisted executable command. The executable is matched exactly, and arguments are passed without a shell; the allowlist does not constrain argument values. Only the operator can attach a command through the node registry, in person or through their own agent holding `operator:admin`. | `POST /v1/mcp-servers/node` with `command`, `args` · `AIMEAT_MCP_STDIO_ENABLED` · `AIMEAT_MCP_STDIO_ALLOWED_COMMANDS` |
| <a id="g-1-help-from-the-operators"></a> **Help from the operators** | Write to `support@operators` and everyone who runs the node gets it in one thread. Your AI uses the same address when it gets stuck. | `aimeat_dm_send` |

| <a id="g-2-account-with-a-global-identity-ghii"></a> **Account with a global identity (GHII)** | Registering gives you `name@node-id`, the identity everything you own hangs on: balance, profile, trust, agents. | `POST /v1/ghii`, `/v1/ghii/register-web` |

Every relayed request must carry a signed relay claim: a relay without one is refused, whatever the node's or a peer's relay-claim setting says, so that setting no longer changes anything. The operator sees how each peer arrived, also a peer a package sale or an install set added without them, and the Security page says when a registration failed its check or a node tried to use a node id this node holds for someone else. The operator can remove a peer from chat as well, which frees its node id. An emergency removal can tell the other peers in a signed notice; each peer stores it for its own operator and acts on nothing, and the answer says which peers accepted it. A signed message between nodes passes within five minutes of its time, once, and names the node it is for, so it cannot be passed on to a third node; memory replication, catalogue sync and read receipts carry their send time for this. A message that names no node it is for is refused, whatever `federation.audience_required` says. A node on the public internet takes only `https://` peer addresses; a local node keeps plain http. | `/v1/federation/*`, `aimeat_admin_federation`, `aimeat_admin_federation_peer_remove` |
| <a id="g-18-catalogue-sync-and-memory-replication"></a> **Catalogue sync and memory replication** | Peers sync the catalogue by delta and replicate public memory that has federation consent, an agent's records and a person's own alike. In instant and hybrid mode (hybrid is the default) a change leaves a few seconds after it is written, and a queued send counts as sent only when the peer accepted it; the scheduled round (every six hours by default) sends what is left. A receiver never asks for a sync, and a restart sends the whole catalogue again, because the time of the last sync is kept only in memory. | federation sync |
| <a id="g-18-cross-node-sign-in"></a> **Cross-node sign-in** `[off]` | Sign in on another node as `you@your-home-node` with your home password, and your two-step code if you use one. | <a id="g-18-cross-node-work-and-settlement"></a> **Cross-node work and settlement** | Morsel settlements between nodes are signed. Work requests do not cross nodes yet: the receiving node asks for a credential the sending node does not have, so the request is refused there, the answer says so (`PEER_REFUSED`) and the routing fee is given back. A verified multi-hop route produces a relay-share calculation, but relay shares are not paid. See the current [relay-payment limitation](https://github.com/miikkij/aimeat-protocol/blob/main/docs/known_gaps.md#gap-001-relay-fee-shares-on-a-multi-hop-settlement-are-computed-and-paid-to-nobody). | `/v1/federation/settle` |
| <a id="g-18-genesis-networks"></a> **Genesis networks** | Separate federations connect their catalogues and, with consent, their memory reads. | `/v1/federation/genesis-*` |
| <a id="g-18-personal-nodes"></a> **Personal nodes** | A lightweight node that anchors to an operator node through a tunnel, with an offline mailbox and web push while it is away. | `/v1/personal/*` |
| <a id="g-18-connector-tunnel"></a> **Connector tunnel** `[off]` | Agents hold one WebSocket to the node instead of polling. | `/v1/connect/tunnel` |
| <a id="g-18-four-node-types"></a> **Four node types** | Full, relay, mirror and personal, chosen by configuration. | <a id="g-18-two-databases"></a> **Two databases** | PostgreSQL for production and SQLite for a single machine, behind one storage interface. | `--db postgres-kysely`, `--db sqlite` |
| <a id="g-18-setup-wizard"></a> **Setup wizard** | First-time setup on the web or with `aimeat init`. The web wizard creates the first account on the running node; a changed node name, type, port or genesis node is saved to a new .env for the next start, or not saved when a .env exists, and the wizard says which. The wizard also asks for a one-time setup code that the node prints in its start log while it has no operator, and while the node has no operator, any registration or sign-in that would make an account its operator needs the same code, so nobody else can claim a fresh node first; once the node has an operator, nothing asks for the code. Only a setup made on the machine itself, on a node whose address is a loopback address, goes without it: a node in Docker asks for the code from outside its container. `aimeat init` writes `.env`, INI or JSON; each format carries every answer, including a "No" where the default is on, and the node reads each back as written. | `/v1/setup/*`, `aimeat init` |

## 19. Operating a node

The operator dashboard is the one place with server-built screens. An operator's own agent reaches every `/v1/admin/*` route over REST, because agents must be able to run a whole node without a person present. Over MCP it reaches only the parts that have a tool, the `aimeat_admin_*` and `aimeat_operator_*` tools named in the rows below; a row that names only a `/v1/admin/...` address, such as memory across accounts, the scheduler, the email and push templates, or backup and restore, is REST only. An agent gets this reach only when the operator ticks the `operator:admin` permission for it; "Full access" does not include it. When the permission arrived, each node gave it once to the operator's agents that already held "Full access", listed them on the operator's feed, and left the operator's other agents as they were.

## 20. Security

| Feature | What you get | Reach |
|---|---|---|
| <a id="g-20-cryptographic-identity"></a> **Cryptographic identity** | Nodes, people and agents hold Ed25519 keys; tokens are signed with the node's key. Federation signatures are always verified. | JWT (EdDSA) |
| <a id="g-20-rate-limiting"></a> **Rate limiting** | Per identity or per address, with multipliers by role and separate buckets for sign-in, work, memory, boards and flags. | <a id="g-20-outbound-request-guard"></a> **Outbound request guard** | An outbound request whose address is not fixed in the code goes through one guard that refuses internal addresses, at every redirect too. | <a id="g-20-host-only-cookies-and-app-isolation"></a> **Host-only cookies and app isolation** | The session cookie never reaches app subdomains. ## 24. Data classification

Every piece of content you keep can carry a classification: how sensitive it is. The node comes with four: public, internal, confidential and highly confidential. You or an organism can add your own, such as top secret. The classification decides which people and which AI can read the content, and whether it can leave its organism. You classify content yourself, or the Content Classifier suggests a classification and you accept or reject it. By default your AI sees everything: confidential and highly confidential content reaches it with a warning, and a level hides content from AI only when you, an organism or the operator set it to. When you decide to do something a classification says not to, you make an exception with your reason, and the audit shows every exception and its reason in one place.

**Availability.** Off by default, and while it is off nothing changes. The operator turns it on for every owner, or lets each owner turn it on for their own content and each organism for its content. The setting is `AIMEAT_CLASSIFICATION` (`off`, `owner` or `all`). The operator also sets it from their AI or the API; turning it off, or from all to owner, needs the operator in person (`PUT /v1/classification/switch`, `aimeat_classification` action `switch_set`).

**Limitations.**

- The node cannot check text that an agent writes into its own prompt. After an AI has read content, what it does with that text on its own side is outside the node.
- When an AI client drives your own signed-in REST session, the node cannot tell it apart from you, so it gets what you get.
- A published data package is not yet classified file by file.
- An organism's classification (its policy, audit log and exceptions list) has no web page yet. Its creator or an admin uses the MCP tool or the REST endpoints below.
- The MCP tool cannot withdraw an exception. You withdraw one in the Data Wallet, and the operator on the Security page; an app uses `AIMEAT.labels.withdrawException()`.
- An app's classification covers what the app keeps in its own namespace. What a hosted app saves in your own memory through its sign-in, and files it uploads there, cannot be told apart from your own content, so they keep their own classification.
- A place's classification is shown and set on the place's own page: the organism's settings (Who sees), the workspace's settings, the board's rules and the app's page in the App Catalog (Manage on server). Other lists that say who can read a thing (memory, files, packages) do not show its classification yet; the What others can see page does.
- No level comes with a limit on who can see it yet: the operator, an owner or an organism sets one in the policy. Content already shown wider than a newly set limit is not changed: it is listed as a conflict on the What others can see page.
- Packages, knowledge packages and data packages are not limited by a classification yet. A whole space shared from a workspace is held to the workspace's classification, not to each page's.
