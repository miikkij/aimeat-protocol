What an AIMEAT node does today. Node version 4.0.3, checked against the code on 2026-10-18.

AIMEAT (AI Memory Exchange and Action Transfer) is a place where a person keeps what they know, and where their own AIs, other people's AIs and the apps they build can read it, act on it and share it, under the person's consent. The main road in is the AI chat the person already uses, connected over MCP. The web pages show what happened and hold the controls that need a screen.

This list covers two layers:

- Core is the protocol any node can implement: identity, memory, consent, organisms and workspaces, pacing, federation. Specified in AIMEAT-Core-2026-11.md, normative since node 4.0.0; before it, AIMEAT-RFC-v4.0-Core-full.md with its errata.

- Platform is what the aimeat.io reference implementation builds on it: apps, the agent fleet, extensions, AI, commerce, the web surfaces. This list is its inventory, and the Platform reference says how it is put together; it replaces AIMEAT-RFC-v4.0-Platform-full.md since node 4.0.0.

The API contract is openapi.yaml. Where this list and the contract disagree, the contract wins. Individual apps built on the node (Lifecycle Central, the Design Book's apps, games) are not listed here; they are users of these features.

Markers. off means the feature ships but stays off until the operator switches it on. testnet means it defaults to a test network. Unmarked features are implemented; use can still require configuration, credentials, permissions or an installed runtime. This guide does not report which services a particular node has enabled.

Reach names the REST prefix and the MCP tool family, so a developer can find the door. An MCP tool family written aimeat_task_* means every tool starting with that name.

1. Connecting an AI

The preferred way to use AIMEAT is to talk to it through your own AI. Everything below exists so that the chat path works first and the screen is the fallback.

3. Agents and machine identity

Agents are first-class users. Registration creates a person only; an agent arrives when the person approves it.

Feature What you get Reach
Agent identity (GAII)Every agent has agent#owner@node-id, its own scoped permissions and trust score, and acts in the owner's name. Owners can organise agents with tags, change their granted access and delete an agent identity. Deleting an agent cancels its open work, and the morsels held for it go back to whoever asked; its finished work stays in the other side's records under the agent's name. The outside accounts the agent connected are removed with it, so a new agent given the same name sees none of them. The trust score is worked out again and stored each time the agent's profile is read over REST; your AI's aimeat_agent_profile shows the stored score, which can be older./v1/agents, /v1/agents/:name, aimeat_agents_list, aimeat_agent_profile
Device authorization (RFC 8628)The agent shows a code; you approve it in the browser and pick its scopes. The standard agent path. When nobody picks any, the agent may read, write and delete your memory (a record it deletes goes to the bin, and you can put it back for seven days; removing anything for good, or deleting an organism, takes a permission you grant separately), read the catalogue, read the workspaces of your organisms, see your other agents, send messages for you (signed as your agent) and save files; the "standard" choice on the approval page also lets it write and publish there. A ChatGPT or claude.ai connection approved on the sign-in page gets the same list. One of your agents that holds the permission to make agents (agent:write) can approve another of yours without you, and gives it only permissions it holds itself./v1/agents device flow, scopes.default_agent_scopes (AIMEAT_DEFAULT_AGENT_SCOPES)
What an agent was refusedWhen the node refuses one of your agents a call for a permission it lacks, you see it without reading a log: on the agent's card, with the permission in words and a button that lists every missing permission at once, so you give all of them, some of them, or decline them; on each of its open tasks, as an event in the task's history; and in your AI's list of agents. The card also shows what the agent asked for when you approved it and what of that you did not give. The agent can read its own refusals, so a runtime can tell after a run that it did not do everything it tried; the CrewAI daemon then fails the task with the reason instead of reporting success. A refused agent counts as an agent with a problem on the agents page. A refusal goes away when you give the permission or decline it (a declined permission stays declined on every route, and the agent is still told), ages out after 14 days, and goes with the agent. When the node cannot read the refusals, the agent list says so (refusals_unreadable) instead of showing none, and a refusal still waiting to be written is written when the node shuts down. An agent connected with aimeat connect add --scopes asks for its permissions up front.Agents > the agent's card, GET /v1/agents (refusals, scope_request), GET /v1/agents/:name/refusals, POST /v1/agents/:name/refusals/decline, aimeat_agents_list, task event scope_denied
Allow with one pressWhen your AI tries something you have not allowed yet, it does not tell you the name of a permission. It gives you one address, and the page there asks one question in your language: what the agent wants to do, with Allow and Don't allow. Press Allow and the AI goes on in the same conversation: a ChatGPT or claude.ai connection renews its access by itself. The tools your AI could use once you allow them stay on its list, so it never says the node cannot do something. You also get the same question in the bell, with an Allow button, and by email (switch it off on the Email page), once per request. Limits: one press gives only what "Full access" carries and the node does not call powerful; anything else (removing for good, AI spending, your mailbox as you, node administration) is the agent's own page, and the AI is given that address instead. Existing agents can migrate in a batch; the Agents page reports failed sign-ins. Personal access tokensRevocable tokens with chosen scopes, or a token that acts as you in full, with an optional expiry, exchanged for a short-lived token. Limits: the read_owner_data field is accepted and stored, but nothing reads it, so it gives the token nothing./v1/access/tokens, POST /v1/auth/token/exchange
Ecosystem apps (GEAI)A third kind of principal, eco:app#owner@node-id, for outside applications: onboarded through hello, approve and token with key pinning, limited to approved scopes and data areas, revocable like an agent. Signed challenge sign-inAn agent signs its identity and a timestamp with its keypair and gets a token; no nonce is fetched or spent. Key rotationRotate an agent's keypair; its old tokens stop working, and a connector connection opened with one is closed./v1/agents/:gaii/rekey
Agent portabilityExport an agent and import it on another node. Imported trust is capped at 65. Starting a port takes 50 morsels from your balance (the operator sets the amount). After you delete the agent here, its address sends visitors to the new node for 30 days. Limits: the address forwards only to a node this node peers with./v1/agents/:gaii/export, /v1/agents/import, /v1/agents/:gaii/port
Identity attestationsTwo to four parties co-sign a statement with the keys they already hold on this node. Anyone can read it, and the node checks every signature again each time it is read. Limits: the check is this node's answer; the attestation carries no public keys, so a reader who does not trust the node cannot check it alone./v1/attestations
Document signingAsk up to ten people or agents on the node to sign a document; only its SHA-256 is kept. A person signs with a passkey, which must check them with a PIN, fingerprint or face, and an agent signs as itself with its key or session, never in its owner's name. The node seals each signature with its own key, so a signature can be checked without the node, and anyone holding the document sees who signed it by its hash, with no account. Signing with your session works only on this node's own pages: an app, and a personal access token you made, sign as you only with a passkey, because a press in a program does not show that you pressed. Each person asked to sign is notified; an agent asked to sign is not. 24. Data classification

Every piece of content you keep can carry a classification: how sensitive it is. The node comes with four: public, internal, confidential and highly confidential. You or an organism can add your own, such as top secret. The classification decides which people and which AI can read the content, and whether it can leave its organism. You classify content yourself, or the Content Classifier suggests a classification and you accept or reject it. By default your AI sees everything: confidential and highly confidential content reaches it with a warning, and a level hides content from AI only when you, an organism or the operator set it to. When you decide to do something a classification says not to, you make an exception with your reason, and the audit shows every exception and its reason in one place.

Availability. Off by default, and while it is off nothing changes. The operator turns it on for every owner, or lets each owner turn it on for their own content and each organism for its content. The setting is AIMEAT_CLASSIFICATION (off, owner or all). The operator also sets it from their AI or the API; turning it off, or from all to owner, needs the operator in person (PUT /v1/classification/switch, aimeat_classification action switch_set).

Limitations.

- The node cannot check text that an agent writes into its own prompt. After an AI has read content, what it does with that text on its own side is outside the node.

- When an AI client drives your own signed-in REST session, the node cannot tell it apart from you, so it gets what you get.

- A published data package is not yet classified file by file.

- An organism's classification (its policy, audit log and exceptions list) has no web page yet. Its creator or an admin uses the MCP tool or the REST endpoints below.

- The MCP tool cannot withdraw an exception. You withdraw one in the Data Wallet, and the operator on the Security page; an app uses AIMEAT.labels.withdrawException().

- An app's classification covers what the app keeps in its own namespace. What a hosted app saves in your own memory through its sign-in, and files it uploads there, cannot be told apart from your own content, so they keep their own classification.

- A place's classification is shown and set on the place's own page: the organism's settings (Who sees), the workspace's settings, the board's rules and the app's page in the App Catalog (Manage on server). Other lists that say who can read a thing (memory, files, packages) do not show its classification yet; the What others can see page does.

- No level comes with a limit on who can see it yet: the operator, an owner or an organism sets one in the policy. Content already shown wider than a newly set limit is not changed: it is listed as a conflict on the What others can see page.

- Packages, knowledge packages and data packages are not limited by a classification yet. A whole space shared from a workspace is held to the workspace's classification, not to each page's.
