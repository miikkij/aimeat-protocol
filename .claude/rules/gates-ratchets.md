## Gates for this area

- **Pre-commit hook** (`.githooks/pre-commit`) runs 6 commands and takes about twenty seconds warm: cached lint, three incremental type checks, `check:silent-catch --staged`, and `check:notices` only when THIRD-PARTY-NOTICES.md is in the commit — that file is generated, and a hand edit to it went red on the Security tab four times in two days before the hook asked. **Everything slower is `pnpm gate`, run ONCE when a piece of work is finished** and before it is called done, and it runs only what the change can have reached (`scripts/gate.ts` reads the diff since origin/main and prints its plan with a reason per line): always `check:fast` (the thirty-odd read-only gates, four at a time; `pnpm check:fast --list` names them) and `check:invariants` (the five gates that read the compiler's program, on one program); the unit tests whose import graph reaches a changed file; an E2E suite that itself changed (also under `--full`, and on both backends with `--postgres`); and the guard tier only when something under `src/routes`, `src/auth`, `src/services`, `src/storage`, `src/mcp`, `src/middleware`, `src/utils`, `src/commerce`, `src/server-bootstrap`, `src/config.ts` or `src/config-types.ts` changed, on SQLite (`--postgres` adds the production backend). `pnpm gate:full` runs static checks, all unit tests, changed E2E suites and the guard tier on both backends (not the full E2E sweep) and is for rare occasions: a release, a storage change, a day that touched the identity layer. The pre-push hook checks only that the push is not from behind origin and that the tree boots. CI runs the whole set on every push and blocks a merge on it, so what the gate skipped for cause is still checked, after the fact and on nobody's clock. This split is from 2026-09-05: the hook had been 45 lines and 7–9 minutes a commit, then eight lines and two minutes with a fifteen-minute pre-push, and a day of iterative work is twenty commits — a check that costs minutes on each of them turns a thirty-minute change into a day. Commit and push freely; gate once. `pnpm check:doc-counts` holds the number in this line against what the hook actually runs — add a hook line and this line fails until it is bumped, which is the point. `check:mcp-tools` proves the MCP surfaces expose the same tool NAMES and `check:mcp-schemas` proves they take the same PARAMETERS; the second was written in May 2026, left unwired, and a crew found the defect it had been printing all along. **A new read-only gate goes into `FAST_CHECKS` in `aimeat/scripts/lib/check-registry.mjs`**, which is what `pnpm gate` and CI run — NOT the hook, whose six commands are the list above, so a gate added there is first seen by whoever runs `pnpm gate` and otherwise by CI; `check:audit-gates` is a hand-kept list for running the ratchets alone and answers nothing on its own. A gate that writes the tree (a build, a seed) is its own hook line.
- **Every backlog and when it last fell: `pnpm debt`.** It reads each ratchet file's git history and prints the current count, the count at its first commit, and the last date the number went DOWN. A report, never a gate, and not in the hook: making a number fall is a decision about what to work on. It exists because a ratchet reports ✓ on every commit whether or not the thing it counts has moved, and one of them had not moved in twenty-three days while doing so.
- **How often main goes red, and why: `pnpm ci:stats [--since YYYY-MM-DD] [--json]`.** It reads the CI workflow's runs on main from GitHub and prints each red period (first red run to next green): the failed step, the commit that broke it and the one that fixed it with their `Session:` trailers, the pushes it took, the hours red, and per-week totals. A report, never a gate. The causes need someone to read the fixes, so the watch `watch-ci-punaiset-jaksot` in AIMEAT CODING CENTRAL classifies them and keeps one row per period in workspace `ws-muf3ib6hl4j`, whose readme lists the fields and the causes. Written 2026-09-24, when September had 77 red periods and 62 hours red, and the incidents board had a cause for about 15 of them.
- **A ratchet is seeded, and the seed says what it is.** `security/*.json` and the `ALLOWED` map at the top of a gate script hold today's offenders with a reason each, so the gate fails only on a NEW one and the backlog is countable. Every entry is one of two things: an ANSWER, a sentence saying what makes that code right, or a QUESTION, the placeholder the seeding wrote because nobody had read it yet. The placeholder is worded per file (`Not yet reviewed`, `UNREVIEWED`, `DEBT`), and its own header says which. Triaging one means deleting the entry or replacing the placeholder with the answer; `open-writes` shows what a finished file reads like, and says its result out loud: not one of those doors is a hole, because each is gated inside its handler where a middleware scanner cannot look. Re-seeding forgives the whole backlog, so it is a decision to be asked about, never maintenance. **An ANSWER goes false as easily as code goes wrong, and a repeated answer goes false in bulk.** Twenty-two `identity-resolution` entries in six files carried one copied sentence about a fallback argument a helper took; when the helper stopped taking one, nineteen of those units stopped reading `sub` at all and left the file, and the three that stayed turned out to be reading it for something the copy had hidden. So a sentence you are about to write for the seventh time is a sign the CODE has a shape worth changing instead, and "N listed unit gone" names rows whose reason may have expired before they did (2026-09-12). **Neither the counts nor which files are triaged is written here.** `pnpm debt` prints the counts with the date each last fell, each file's header says what its entries mean, and grepping a file for its placeholder word is what says how much of it is still open. This line used to carry five counts and a triage verdict per file, and by 2026-09-12 all of it had drifted: three counts off by more than half, three `owner-principal` entries still described as OPEN QUESTION when somebody had answered all three, and `route-scopes` called untriaged when every entry but one carried a verdict, the 2026-08-16 triage having read all 339 and four commits on 2026-09-04 having taken the debt column from 179 to five.
- **Which protocol version we declare is a gate, not a memory.** `pnpm check:protocol-versions` reads `security/protocol-versions.json`: every external protocol this node speaks, the version we DECLARE, the version that is CURRENT, and the day somebody last looked. It fails on two things — the ledger no longer describing the code (MCP's revision string is written out in **two** files, and both are checked), and a triaged entry going stale past 90 days. Untriaged entries are counted and never fail; thirteen of the fifteen say so honestly, and one leaves that state by somebody reading the spec, never by re-seeding. **Re-seeding forgives the whole list**, which is the only thing standing between this node and the next wrong answer. Written 2026-09-04, the day an audit of our own MCP and A2A surfaces was wrong three times in one afternoon (the v2 SDK "did not exist" — it is a package split; four A2A task states were "missing" — all eight were produced; results carried "no artifacts" — they did) and an outside scanner, not us, noticed we were declaring an MCP revision two revisions behind.
