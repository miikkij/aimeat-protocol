## Gates for this area

- **One catalog entry, and one handler where it can be.** A tool's input schema, annotations, scope and v2 surfaces live on its catalog entry (`src/tool-catalog/definitions/`), and both MCP surfaces register `zodShapeFor(name)`. A connector MCP tool runs its CLI dispatch definition (`src/cli/connect/mcp/tools/dispatch-tools.ts`) unless it is listed in `security/connector-own-handlers.json`, which only shrinks. `pnpm check:mcp-schemas` holds both lists (secaudit 2026-10, M3).
- **Every tool the node offers over MCP is offered by `aimeat connect serve`, on both of its interfaces.** A tool registered on the node MCP is registered on the connector MCP and has a handler behind `/local/call/<tool>`, unless `security/connect-serve-parity-exemptions.json` names it with a written reason (Jouni, 2026-10-12: "kaikki mitä MCP:tä tehdään pitää olla aimeat connect servessä tarjolla agenttien käytettäväksi"). So a new node MCP tool ships with a CLI dispatch definition in `src/tool-dispatch/tool-call-defs-*.ts`, a thin proxy over the REST route the tool uses; `dispatch-tools.ts` then registers it on the connector MCP, and `test/unit/cli-tool-param-forwarding.test.ts` invokes it. The handler decides nothing: the scope check, the validation and the provenance stay in the route. `pnpm check:mcp-tools` (`scripts/audit-mcp-tools.ts --check`, in `check:fast`, `pnpm gate` and CI) holds it by comparing REGISTRATIONS, and then holds the catalog's three visibility flags (`publicMcp`, `connectorMcp`, `cliFallback`) to what is registered, in both directions, for every tool. It was written because the gate before it asked for a handler only where the catalog declared `cliFallback: true`: 30 agent tools declared false, had no handler, and the gate passed, and 21 of them declared `connectorMcp: false` while the connector registered them. A flag the tool's author sets cannot decide whether the tool is checked. The exemptions file follows the ratchet rules (`gates-ratchets.md`): each entry is an answer read from the code, an entry whose tool is offered on both interfaces fails until it is deleted, the count is `EXEMPTION_CEILING` in `scripts/inventory/connect-serve-parity.ts` so the list only shrinks, and a new entry or a re-seed is a decision for Jouni. A tool on the connector and not on the node MCP declares `connectorOnly` and has its reason in `V2_EXCLUDED` (`src/tool-catalog/surfaces.ts`). The node MCP's names are read from the registration (`captureServer`), because a tool registered from a variable has no source line a scan can find: two were reported as connector-only for that reason.
- **A tool has THREE surfaces, not two.** The node MCP (`src/mcp/`), the connector MCP (`src/cli/connect/mcp/tools/`), and the CLI dispatch behind `/local/call/<tool>` (`CONNECT_CLI_TOOLS` in `src/cli/connect/tool-call.ts`, built from the definitions in `src/tool-dispatch/tool-call-defs-*.ts`), which is what a fleet daemon actually calls. A parameter added to the first two does not exist on the third, and it is dropped in silence, so the call succeeds having done less than it was asked. That cost the same defect three times in one week, each found by a crew rather than by us. Two things now stop it: the dispatch REFUSES an undeclared parameter instead of ignoring it (`withDeclaredInputOnly` in `tool-call.ts`, one wrapper on the assembled table so neither door can miss it), and `test/unit/cli-tool-param-forwarding.test.ts` INVOKES every handler against a recording client and fails if a published parameter never leaves the process. Do not gate this by reading handler source: that was tried on 2026-08-16 and was wrong in both directions inside an hour. And the drift is not always a parameter: the same tool NAME meant two different backends for months — `aimeat_app_*` served the 50 single-file apps at `/v1/apps` on the node and the 4 component packages at `/v1/packages` on both connector doors, so a fleet agent could not reach one real app. Packages are `aimeat_package_*` now. When a catalog DESCRIPTION and its own `input` disagree, believe neither and read the route. It reads the worktree rather than the index, so an uncommitted fix can green it falsely. CI runs the same set plus the vitest suite. A second hook, `.githooks/commit-msg`, checks the message itself.
- **A new MCP tool failure is `toolError(code, message)`** from `src/mcp/tool-error.ts`: the text reads `CODE: what happened`, with the same code the REST door answers (NOT_FOUND, INVALID_INPUT, SCOPE_DENIED), so a test asserts the code and not the sentence. Do not write the support address into it: `error-next-step.ts` appends what to do next to every failing tool result, in one place. The 333 failures written before 2026-09-19 stay in their three shapes (157 plain sentences, 80 JSON objects, 48 `CODE: message`), because suites and clients read those texts as they are and a good model reads all three; convert one only when you are changing that tool anyway.
- **The Python package is held to the node by two gates, and the node schema wins.** `pnpm check:python-shapes` compares the offer and signal fields `build_offer`, `build_offers_doc` and `Sig` write (read from the Python source) with the zod schemas, and holds `python/aimeat-crewai/tests/fixtures/node-offer-schema.json` to them; after a change to `offer-schemas.ts` or `workflow-signals.ts`, `pnpm python:schema` rewrites the fixture and `tests/test_node_schema_parity.py` validates what the builders return against it. `pnpm check:python-daemon` compares the loopback routes `daemon.py` calls with the ones the serve daemon registers, the node REST routes each side calls, and the MCP tool names the package uses with the connector's. A difference is fixed on the lagging side or listed with its reason in `security/python-shape-parity.json` or `security/python-daemon-parity.json`; both only shrink. Neither sees what a field means: the open `_space_contract` incident (namespace against object type name) passes both. The gate has no Python, so the pytest runs in the package's own CI workflow. (2026-10-18)
